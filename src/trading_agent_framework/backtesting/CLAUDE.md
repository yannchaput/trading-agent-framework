# backtesting/ -- the third trading mode

> Nested `CLAUDE.md`; project-wide rules are in the root `CLAUDE.md`. Paths are relative to `src/trading_agent_framework/` unless they start with `tests/`, `scripts/` or `docs/`.

## Architecture

- `backtesting/` -- the third trading mode. `clock.py` (`BacktestClock`, simulated time), `broker.py` (`BacktestBroker`, simulated fills via `fills.py`'s pure OHLC rules), `ledger.py` (fills/equity/indicator lines, `Decimal`), `data/` (`BacktestDataSource` ABC, `CachedDataSource`, `YahooBacktestData` default, `AlpacaBacktestData`, `YearChunkedData` in `chunked.py`: minute bars one 365-day chunk at a time, each fetched from 30 days before its start, for windows over a year; day bars and sessions from one whole-window source), `warmup.py` (**pure** `warmup_calendar_days()`, approximating a trading-day lookback as a calendar-day buffer), `metrics.py` (vectorbt reporting) and `report.py` (writes the run to `logs/<strategy>/backtesting/<ts>_backtesting/`) are the pure-to-I/O layers; `runner.py` orchestrates a run and `Strategy.run_backtesting()` is the public entry point. Both `Strategy.run_backtesting()` and `runner.run_backtest()` accept a `warmup_trading_days` parameter that widens only the eager benchmark data load's start bound (via `warmup_calendar_days()`), never the simulated `[start, end]` session window itself. The executor itself needed no changes -- `MarketClock.max_wait_slice` (`60.0` live, `math.inf` simulated) is the only seam it exposed.
- `backtesting/placeholder.py` -- `PlaceholderBroker`: what `main.py` builds a strategy with in backtesting mode; no network.

## Gotchas

- **`BacktestBroker._source_bars` is the gate** (design spec §5.2): the single place the broker reads a `BacktestDataSource`, and the one defensive check that no returned row closes after the cutoff. Route any new price path through it rather than calling `self._data_source.bars(...)` directly. A source that can't map a bar to a real session must raise `BacktestDataError` rather than fall back to a plausible-looking index -- silently early data is the failure mode this whole subsystem exists to prevent. `get_bars(..., "minute", include_after_hours=False)` keeps only regular-session rows (close-stamped: `open < ts <= close`, sessions from the data source) and re-reads a longer window through the gate until `length` such rows remain -- Alpaca's minute frames carry extended hours, so the raw last `length` rows covered too few sessions.
- **`AlpacaBacktestData._frames` is keyed by `(asset, timestep)`, never by asset alone.** `runner._run()` eagerly loads the benchmark asset at the strategy's own timestep (e.g. `"minute"`), then separately calls `bars(..., "day")` on the same asset for annualization -- an asset-only cache key let that second call silently reuse the minute-timestep frame relabeled as daily data, with no single obviously-wrong value anywhere (it corrupted `metrics.json`'s benchmark-relative figures -- Sharpe, Sortino, CAGR, alpha/beta -- while `equity.parquet`'s own benchmark columns stayed correct, built via a different path). Any new per-timestep cache in the backtesting data layer needs the same two-part key.
- **`run_backtesting(data_source=...)` takes an instance or a `(start, end)` factory, never the window itself.** A class (`YahooBacktestData`, `AlpacaBacktestData`) or `partial(YearChunkedData, inner=AlpacaBacktestData)` is called as `data_source(warmup_start, end)` (`core/strategy.py`), because only `run_backtesting` knows the warmup-widened start. A source needing extra constructor arguments is bound with `functools.partial` (keyword-only, as `YearChunkedData`'s `inner`), not built up front.
- **One clock advance can span many bars** (minute bars under a sleeptime of hours: `BacktestClock.wait` jumps once and calls `on_advance` once). `_process_pending` therefore walks every bar closed since an order was last evaluated (`_bars_after`), so an order fills on the first bar after submission (next-bar-open, spec §2) and the forming-bar skip costs one bar, not the whole jump. Never evaluate fills on "the latest bar before the cutoff": that filled market orders at hours-old prices, missed limits touched mid-jump, and let a buy fill before the sell submitted ahead of it (rejected for cash).
- **Backtest `start`/`end` must be timezone-aware** (`MarketSession` enforces tz-aware bounds); `run_backtest` validates this up front and says so, so a naive `datetime.now()` never reaches a comparison deep in the clock. **`start`/`end` are inclusive by calendar DATE**: a bare-midnight `end` (how `backtesting_end` is spelled) means "through the end of that day", `sessions()` includes that date's session, and `run_backtest` therefore reads the benchmark up to the last session's close, not the exact instant `end` (a bar is stamped at its close, after that midnight; cutting there dropped the last session -- NaN `benchmark_close`, that day missing from `metrics.json`). Never compare `end` as an instant against a bar timestamp.
- **`equity.parquet` and `metrics.json` are built from the SAME session-reduced series** (`runner._session_equity_samples`): exactly one row per trading session, stamped at the session's close. `BacktestBroker.on_advance` samples equity on every clock advance, so the raw ledger is oversampled several-to-one; feeding that to either consumer silently understates annualised metrics and breaks the benchmark join. Don't hand `ledger.equity` straight to `report.write_equity`.
- **`BacktestBroker` is a long-only cash account, and rejects in two places.** At fill time a buy that costs more than cash (fees included) or a sell larger than the holding is rejected whole (order error status + `OrderEvent.ERROR`, nothing moves); that check stays the authority, since it is the moment cash actually moves. At *submission* time `_projected_rejection_reason` additionally raises `OrderValidationError` for what is already certainly impossible, so a caller finds out in the same iteration instead of a session later -- which matters for an LLM agent, whose only feedback channel is the tool's return value (`submit_order` turns the exception into `{"error": ...}`). The submission check works off ESTIMATED prices (limit price, else the latest close via `_source_bars`) and so deliberately lets through anything it cannot price. It does not break the rebalance pattern that put the hard check at fill time, because `_projection` *credits* pending sells: orders fill in submission order, so sells submitted before buys really do fund them. No shorts, no margin, cash never goes negative. Paper/live trading is unaffected -- all of this lives in `backtesting/broker.py`; Alpaca does its own checks.
- **Backtest fees come from `BROKER`, per order, and differ by side.** `Strategy.run_backtesting(fees=None)` resolves `TradingFeeFactory.from_env()`, so the backtest env file's `BROKER` (Alpaca when unset) picks the schedule; `BacktestBroker(fees=None)` (tests) charges nothing. A sell pays SEC (on value) + FINRA TAF (capped per order) + CAT; a buy pays CAT only -- plus the broker's commission on both (IBKR `max($1, $0.005/share)`, Alpaca $0). Each side rounds up to the cent. Rates are dated constants in `brokers/fees.py` (2026-09-28): an older backtest period pays today's rates. There is no `commission` parameter any more.
- **In backtesting, `get_account()` nets only `buying_power`, never `cash`.** `buying_power` is `_projection(now).cash` (settled cash, minus what pending buys have committed, plus what pending sells will bring in), because backtest fills land a session after submission and a strategy sizing against settled cash double-spends it. `cash` and `portfolio_value` stay raw on purpose: `Strategy.get_cash()` reads `cash`, and `cross_momentum.rebalance` adds its *own* estimate of pending sell proceeds to it, so netting `cash` would make that strategy double-count. That estimate counts only the part of each submitted sell still to fill (`utils.unfilled_sell_proceeds`, read from the `Order` the broker tracks, after `get_cash()`): live market sells fill within seconds and their proceeds are already in Alpaca's `cash`, so adding them again oversized the first buys and got the last ones rejected. In a backtest nothing fills before the next session, so every sell still counts in full. An agent prompt must size buys against the SMALLER of `buying_power` and `cash` + the proceeds of the sells submitted in the same run -- never `min(cash, buying_power)`: raw `cash` ignores the sell credit, so the min always picks it and a same-run rotation buys ~7% of the book (news_binary's 7-share SHV stalls). On a live Alpaca margin account `buying_power` is a multiple of equity, so it must never be named alone either. `NewsBinaryStrategy` also puts a `portfolio` snapshot (balances, positions with `pct_of_portfolio`) in every run's context, because the agent skipped `get_positions` and acted on remembered holdings; a `BacktestError` while building it degrades to a `balance_error`/`positions_error` key rather than skipping the tick (it would never reach the agent-error counter).
- **Backtests simulate trailing stops** (`fills.evaluate_trailing_stop`): `BacktestBroker` keeps each `TRAIL` order's high/low-water mark in `_PendingOrder.trail_reference`, seeded with the latest close at submission, and tests the level from the previous bars *before* a bar's own high may raise it (ties against the trader). `evaluate_fill` still refuses `TRAIL`.
