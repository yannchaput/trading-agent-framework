# brokers/ -- orders, trackers, fees, Alpaca, IBKR and Tastytrade

> Nested `CLAUDE.md`; project-wide rules are in the root `CLAUDE.md`. Paths are relative to `src/trading_agent_framework/` unless they start with `tests/`, `scripts/` or `docs/`.

## Architecture

- `brokers/base.py` -- abstract `Broker` template method (`_conform_order` then `_submit_order`), plus `OrderTracker` wiring. Never imports `alpaca`.
- `brokers/tracker.py` -- `OrderTracker`/`SafeList`: thread-safe order state machine (`unprocessed -> new -> (partially_filled ->)* filled`, or `-> canceled/error`). Used by stream and polling threads concurrently.
- `brokers/factory.py` -- `build_broker()`: the paper/live broker named by `BROKER` (`alpaca` default, `ibkr`, `tastytrade`); broker classes are imported inside the builders.
- `brokers/fees.py` -- **pure** `TradingFeeFactory`: the backtest fee model named by `BROKER` (per-order broker commission + shared SEC/FINRA TAF/CAT regulatory fees), different for buys and sells.
- `brokers/alpaca/orders.py` -- **pure** translation functions only (status/event maps, price conforming, request building, response parsing). No I/O, no state, no client instances. Together with `account.py`, the only modules allowed to import `alpaca.trading.requests` (`market_data.py` is the only one allowed to import `alpaca.data.requests`).
- `brokers/alpaca/broker.py` -- `AlpacaBroker`: wires the real `TradingClient` and `StockHistoricalDataClient` I/O to the pure modules plus tracker bookkeeping. Contains no translation logic itself.
- `brokers/alpaca/client.py` -- trivial factory functions for building Alpaca SDK clients from credentials, so tests can inject fakes instead.
- `brokers/news.py` -- `NewsProvider` protocol (no alpaca import, no I/O), reached through `Broker.news_provider()`.
- `brokers/alpaca/news.py` -- `AlpacaNewsProvider`: the I/O wrapper over the pure `market_data` news functions (imports `client` only, never `alpaca.data.requests`).
- `brokers/alpaca/stream.py` -- `AlpacaTradeStream`: trade-update handler and thread lifecycle for the live order stream.
- `brokers/__init__.py` -- lazy-imports `AlpacaBroker`/`AlpacaTradeStream`/`AlpacaMarketClock`/`IbkrBroker`/`TastytradeBroker` via module `__getattr__` so `import trading_agent_framework.brokers` alone doesn't pull in `alpaca`/pandas/`ib_async`/`httpx`/`websockets`.
- `brokers/alpaca/account.py` -- **pure** account and calendar translation (same rules as `orders.py`).
- `brokers/alpaca/market_data.py` -- **pure** market-data translation (same rules as `orders.py`): timesteps (`"minute"`/`"day"` only), the calendar-based bars window, request builders (IEX; `build_bars_request(feed="sip")` for backtests), and bar/trade/quote parsing.
- `brokers/alpaca/clock.py` -- `AlpacaMarketClock`: sessions (early closes included) from Alpaca's calendar, cached ~10 trading days.
- `brokers/alpaca/data.py` -- `AlpacaMarketData`: Alpaca IEX prices/quotes/bars and the calendar client, shared by `AlpacaBroker`, `IbkrBroker` and `TastytradeBroker`.
- `brokers/ibkr/` -- `IbkrBroker` over the TWS API (`ib_async`, IB Gateway): **pure** `orders.py`/`account.py`; `client.py` (`IbkrConnection`, the only thread/asyncio code: every `IB` access goes through `call()` on its loop thread, with timeouts and reconnect); `events.py` (`IbkrOrderEvents`, feeds `OrderTracker` only); `broker.py` (wiring; market data, clock and news come from Alpaca).
- `brokers/tastytrade/` -- `TastytradeBroker` over Tastytrade's REST API and account streamer: **pure** `values.py`/`account.py`/`orders.py`; `client.py` (`TastytradeSession`, the only HTTP code: OAuth token refresh under a lock, GET retries, writes never retried, `TastytradeHTTPError`/`BrokerUncertainError`); `stream.py` (`TastytradeAccountStream`, the only websocket code: heartbeats, reconnect then `reconcile`); `events.py` (`TastytradeOrderEvents`, feeds `OrderTracker` only); `broker.py` (wiring; market data, clock and news come from Alpaca).

## Gotchas

- **Never let a raw SDK/pydantic exception escape.** Wrap broker failures in `BrokerError`/`OrderValidationError`/`OrderEventError` (see `errors.py`). `orders.py`'s `validate_order` wraps pydantic `ValidationError`; `AlpacaBroker._submit_order` wraps client exceptions via `order.set_error(exc)` *before* re-raising (lumibot compatibility contract -- don't reorder this).
- **`orders.py`, `account.py` and `market_data.py` stay pure.** No I/O, no client instances, no state. If you need to call the Alpaca API, that logic belongs in `broker.py`, not here.
- **Market data:** `get_last_price` is the last *trade* (not the quote midpoint; use `get_quote(...).mid`). Live/paper data requests use the IEX feed; Alpaca backtests read SIP bars (`AlpacaBacktestData(feed="sip")`, the default; all exchanges, historical only: Alpaca refuses data under 15 minutes old on the free plan; `feed="iex"` for parity with live; the source's `name` is `alpaca_sip`/`alpaca_iex`, recorded in `settings.json`). IEX is ~2-3% of volume, so a thin stock has no bar in many minutes and a simulated stop fills late or never. Backtest signals therefore come from cleaner data than live ones. Bars are split/dividend-adjusted. `get_bars` makes one `get_calendar` call to start its window at the right session. Nothing is cached: every call hits the API (200 requests/min on the free IEX plan).
- **`ib_async` stays inside `brokers/ibkr/`** and `import trading_agent_framework.brokers` never imports it. Never call `IbkrConnection.call()` from a function passed to `call()`: it already runs on the loop thread and would deadlock.
- **IBKR order identity is ours.** `identifier` is our id and `orderRef` carries `{strategy}:{identifier}`; `modify_order` edits in place and returns the same `Order`. Orders placed by another `IBKR_CLIENT_ID` are tracked but cannot be cancelled or modified.
- **IBKR order-status hand-off.** While `_submit_order` waits (order `UNPROCESSED`) it owns rejections; once it returns, the order is `SUBMITTED` and `IbkrOrderEvents` owns every later transition.
- **IBKR margin check is a heuristic, and only runs live.** IBKR's API does not say cash vs margin; `ibkr/account.check_account` treats buying power above ~1.05x cash as margin and refuses to trade. It does not check this on paper: IBKR's paper-trading simulator reports `BuyingPower` at ~6.67x cash on an account confirmed (web portal, plus `InitMarginReq`/`MaintMarginReq`=0 and `Cushion`=1 in that same summary) to be a genuine cash account -- paper's simulated buying power doesn't reflect the linked account's real cash/margin restriction, so the check is guaranteed noise there and would always warn regardless of the real setting.
- **IBKR blocks EU/EEA retail accounts from most US-domiciled ETFs (SPY, QQQ, ...).** PRIIPs requires a KID (Key Information Document) in an approved language before a retail client can buy one; US ETF issuers don't publish one, so the order is rejected (`Inactive`, IBKR error 201 "No Trading Permission"), with `Inactive`'s `trade.log` entry sometimes carrying no message at all -- the real reason only ever arrives via the `errorEvent` callback, which `_place_and_wait` also captures and hands to `orders.rejection_message` as a fallback (`smoke_ibkr_orders.py` trades a plain stock for exactly this reason: the restriction is ETF/packaged-product-specific, not company shares).
- **Tastytrade has no trailing stops** (`OrderType.TRAIL` is rejected, so `earnings_drift` can't trade there) and takes fractional quantities on market orders of `is-fractional-quantity-eligible` stocks only: a fractional limit/stop is rejected (a floored stop would leave the remainder unprotected), a non-eligible fraction or notional is floored to whole shares with a warning.
- **Tastytrade order identity.** `external-identifier` carries `{strategy}:{identifier}`, but events find orders by Tastytrade's order id: a modify is a cancel-and-replace with a new id, and the old id is superseded from the moment the PUT is sent (its fills count, its `Cancelled` is ignored). `modify_order` returns the same `Order`.
- **Tastytrade does not deduplicate orders.** Writes are never retried (`client.py`). A submit or modify whose outcome is unknown (timeout, transport failure, 5xx on a write, 2xx with no order id) raises `BrokerUncertainError` and is **never resent** (`BrokerUncertainError` is for writes only: a failed GET, retries exhausted, is a plain `BrokerError`): the order stays tracked as `SUBMITTED` (a modify's original stays superseded) and is resolved later by lookup on `external-identifier` -- found, it is adopted; a clean miss only counts after 2 misses at least 30 s apart (`UNKNOWN_WRITE_GRACE`), then the submit fails with an error event or the modify is restored. The lookups run on stream reconnect (`reconcile`) and at `pull_order`/`pull_orders`/`cancel_order`/`modify_order`; cancel and modify of an order with an unresolved write raise `BrokerUncertainError` instead of sending. The account stream adopting the order always wins.
- **KNOWN LIMITATION: the strategy desks don't handle `BrokerUncertainError` yet.** `vwap_pullback/desk.py`, `earnings_drift`, `congress_trades`, ... wrap `submit_order` in `except Exception` and read it as "order not placed". On `BROKER=tastytrade` a timed-out stop POST would then trigger a market sell that leaves an orphan stop, and a timed-out buy would be resubmitted (a double buy). Before running them on Tastytrade live, each desk must catch `BrokerUncertainError` first and treat the order as pending. `Strategy.cancel_orders`/`cancel_open_orders` also stop at the first `BrokerUncertainError`.
- **The Tastytrade sandbox fills are synthetic** (market at $1, limits under $3 fill at once, $3 or more never fill; daily reset), so `main.py` refuses to run a strategy with `BROKER=tastytrade` and `BROKER_API_IS_PAPER` not false. The sandbox is for `scripts/tests/smoke_tastytrade_*.py` only.
- **Tastytrade margin check.** `tastytrade/account.check_account` refuses a margin account live (`margin-or-cash`) and only warns in the sandbox (the sandbox accounts are assumed to be margin: provisional, see below).
- **Provisional Tastytrade values pending the sandbox probe** (design spec section 11): `orders.FRACTIONAL_QUANTUM` (0.00001), the account streamer's `auth-token` format (`stream.auth_token_value` sends `Bearer <token>`; the spec says the bare token -- one line to flip), the `BRK.B` <-> `BRK/B` symbol mapping, "sandbox accounts are margin" and some response field names. Confirm them against `scripts/tests/probe_tastytrade_orders.py` output.
- **`httpx` stays in `brokers/tastytrade/client.py` and `websockets` inside `stream._default_connect`**; `import trading_agent_framework.brokers` imports neither.
